SSR, SSG e ISR: quando o HTML nasce

Até aqui a Ana achava que "página" era um arquivo HTML pronto na pasta. No Next.js a página pode nascer na hora do pedido, nascer uma vez no build ou nascer estática e se renovar sozinha — três ritmos diferentes para a mesma tela. Nesta aula você aprende a escolher o ritmo certo para cada página do app dela.

Você vai aprender
  • SSR (dinâmica): o servidor monta o HTML a cada pedido — export const dynamic = 'force-dynamic' e fetch(..., { cache: 'no-store' })
  • SSG (estática): o HTML é gerado uma vez, no build — o padrão quando dá para
  • ISR: estática, mas o servidor recria a página sozinha depois de export const revalidate = 60 segundos
  • generateStaticParams() para gerar as rotas dinâmicas [slug] no build
  • O que o fetch cacheia por padrão no App Router (diferente do React puro!)

A ideia: o restaurante da esquina

Imagine o restaurante da esquina da Ana. Alguns pratos são feitos na hora: o cliente pede, a cozinha prepara na hora e entrega fumegando — demora um pouco, mas sai sempre fresquinho. Isso é o SSR (Server-Side Rendering): cada pedido ao servidor vira um HTML novo, montado na hora, com os dados atuais (hora do servidor, usuário logado, carrinho). É perfeito para páginas que precisam parecer "vivas" em cada acesso.

Outros pratos ficam prontos no freezer: foram preparados uma única vez (no build, quando o deploy foi feito) e são servidos instantaneamente a todo mundo, sempre iguais. Isso é o SSG (Static Site Generation): o HTML nasce uma vez e fica num CDN, servindo cópias idênticas em milissegundos. É perfeito para páginas que não mudam sozinhas — um blog, uma página Sobre, um catálogo.

E existe o meio-termo, o prato que a cozinha retira do freezer e refaz de tempos em tempos: a primeira pessoa depois de 60 segundos recebe a versão nova, e ela fica no freezer de novo até a próxima fornada. Isso é o ISR (Incremental Static Regeneration): a página é estática (rápida), mas o servidor a recria em segundo plano quando o tempo revalidate passa. É o melhor dos dois mundos para notícias, preços e estoques que mudam de vez em quando.

Como o Next.js decide o ritmo

No App Router, a regra padrão é: se dá para gerar no build, o Next.js gera estático. O fetch dentro de um Server Component vem cacheado por padrão (diferente do React puro, onde cada fetch é novo) — ou seja, o padrão puxa para o SSG. Para forçar o SSR, existem duas portas: ler dados que só existem no pedido (cookies(), headers(), searchParams) ou declarar na rota:

// app/page.jsx — HOME DINÂMICA (SSR): HTML novo a cada pedido
export const dynamic = 'force-dynamic';

async function getHoraAtual() {
  const res = await fetch('https://worldtimeapi.org/api/timezone/America/Sao_Paulo', {
    cache: 'no-store', // sem cache: busca nova a cada renderização
  });
  return res.json();
}

export default async function Home() {
  const dados = await getHoraAtual();
  return (
    <main>
      <h1>⏰ Agora no servidor: {dados.datetime}</h1>
      <p>Recarregue a página: a hora muda a cada acesso (isso é SSR).</p>
    </main>
  );
}
// app/blog/page.jsx — LISTA DE POSTS ESTÁTICA (SSG): gerada uma vez no build
async function getPosts() {
  const res = await fetch('https://jsonplaceholder.typicode.com/posts');
  // SEM cache: 'no-store' => o fetch fica cacheado e a página vira estática no build
  return res.json();
}

export default async function Blog() {
  const posts = await getPosts();
  return (
    <main>
      <h1>📰 Blog</h1>
      <ul>{posts.slice(0, 5).map(p => <li key={p.id}>{p.title}</li>)}</ul>
    </main>
  );
}
// app/noticias/page.jsx — ISR: estática, mas recriada a cada 60 segundos
export const revalidate = 60;

async function getNoticias() {
  const res = await fetch('https://jsonplaceholder.typicode.com/posts', {
    next: { revalidate: 60 }, // o fetch também aceita revalidate (vem ganhando do route segment)
  });
  return res.json();
}

export default async function Noticias() {
  const noticias = await getNoticias();
  return <main><h1>🗞️ Notícias (atualizadas a cada 60s)</h1></main>;
}
// app/blog/[slug]/page.jsx — rotas dinâmicas estáticas no build
export async function generateStaticParams() {
  const posts = await fetch('https://jsonplaceholder.typicode.com/posts').then(r => r.json());
  return posts.slice(0, 10).map((p) => ({ slug: String(p.id) })); // /blog/1, /blog/2…
}

export const dynamicParams = false; // slugs fora da lista dão 404 (em vez de SSR na hora)

export default async function Post({ params }) {
  const { slug } = await params; // Next.js 15: params é uma Promise
  return <main><h1>Post #{slug}</h1></main>;
}

Quando dá errado

Erro clássico de build: a Ana colocou fetch(..., { cache: 'no-store' }) numa rota que também usa generateStaticParams(). Na hora do next build, o Next.js reclama porque não dá para gerar no build uma página que busca dado novo a cada hora:
Error: Route "/blog/[slug]" used `cache: 'no-store'` inside a route that uses
`generateStaticParams`, preventing the route from being fully static.
→ tire o 'no-store' (aceite ISR com revalidate) ou remova o generateStaticParams.
Outro clássico: a página era para ser estática, mas usava cookies() sem querer, e o Next.js imprime no terminal (modo dev) um aviso de "uso dinâmico do servidor" — a página passou a ser SSR sem a Ana perceber:
Dynamic server usage: Route / couldn't be rendered statically because it used `cookies`.
See more info here: https://nextjs.org/docs/messages/dynamic-server-usage
→ ou abra mão do estático (dynamic = 'force-dynamic') ou remova a leitura de cookies da página.
