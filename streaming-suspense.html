Streaming e Suspense: a página chega em partes

A Ana reparou que algumas páginas dela demoravam demais para mostrar qualquer coisa: o visitante ficava olhando para uma tela branca até o último dado chegar. Com streaming, o Next.js manda o HTML em pedaços: o miolo rápido chega na hora e as partes lentas vão entrando depois, no lugar certo. Nesta aula você monta isso com <Suspense>, loading.jsx e componentes async.

Você vai aprender
  • O que é streaming de HTML (o servidor manda <div hidden> + um <script> que troca o conteúdo quando chega)
  • <Suspense fallback={...}> em volta de componentes async no Server Component
  • loading.jsx: o fallback automático de um segmento inteiro da rota
  • Por que a página inicial fica mais rápida (TTFB menor) mesmo com dados lentos
  • O limite: useSearchParams() dentro de página estática precisa de Suspense

A ideia: o jornal que imprime a manchete antes da charge

Imagine um jornal que só sai da gráfica quando a charge do dia fica pronta — se o chargista atrasa, ninguém recebe nada. Isso é a página sem streaming: um componente async lento segura o HTML inteiro. Agora imagine o jornal que imprime a manchete primeiro e, na mesma dobra, um espaço em branco com um "desenho chega já já": o leitor já tem o essencial na hora, e a charge entra no espaço reservado quando fica pronta. Isso é o streaming com Suspense.

Tecnicamente, o servidor manda o HTML em fluxo contínuo (chunked): primeiro o "shell" (cabeçalho, menu, texto) já utilizável, e as partes suspensas vão como blocos escondidos (<div hidden>) junto de um pequeno <script> que, quando os dados chegam, troca o fallback pelo conteúdo de verdade — sem recarregar a página. O navegador mostra o conteúdo parcial imediatamente e o resto "aparece" sozinho. Para o usuário, a página parece muito mais rápida; para o servidor, nada mudou além de não segurar tudo.

O Next.js tem duas formas de declarar o "espaço reservado": o <Suspense> explícito em volta de um componente (controle fino, dentro da página) e o arquivo loading.jsx na pasta da rota (o fallback vale para o segmento inteiro — ótimo para a troca de página inteira).

Ana e o jornal que imprime a manchete primeiro e as páginas depois

O jornal da manhã não espera a última página ficar pronta para entregar o exemplar: a manchete sai primeiro, e as páginas mais pesadas (o caderno de esportes, os classifieds) chegam logo em seguida. O streaming do Next.js faz isso com a página: o que é rápido (menu, título) já aparece na tela na hora, e o que demora (uma tabela com mil linhas, um componente async que busca dados) entra depois, no lugar reservado pelo <Suspense fallback={...}> — o "aguarde um instante" do jornal.

A Ana escreve o componente lento como async (ele mesmo busca os dados com await fetch) e envolve no <Suspense> com um fallback bonitinho (um skeleton, por exemplo). O navegador recebe o HTML em partes (stream) e vai preenchendo — o usuário vê a página "carregando por dentro" em vez de olhar para uma tela branca.

Componente async + Suspense no App Router

import { Suspense } from 'react';
import Recomendados from './Recomendados'; // componente async (lento)
import Comentarios from './Comentarios';   // componente async (lento)

export default function Home() {
  return (
    <main>
      <h1>📰 Portal da Ana</h1>
      <p>Este texto chega na hora — está fora do Suspense.</p>

      <Suspense fallback={<p>⏳ Carregando comentários…</p>}>
        <Comentarios />
      </Suspense>

      <Suspense fallback={<p>⏳ Carregando recomendados…</p>}>
        <Recomendados />
      </Suspense>
    </main>
  );
}
// Componente de servidor async: o await aqui SUSPENDE só este pedaço
export default async function Comentarios() {
  const res = await fetch('https://jsonplaceholder.typicode.com/comments?_limit=3', {
    cache: 'no-store', // dados que mudam: não deixa estático
  });
  const comentarios = await res.json();
  // await new Promise(r => setTimeout(r, 3000)); // teste: simula lentidão de 3s
  return (
    <section>
      <h2>💬 Comentários</h2>
      <ul>{comentarios.map(c => <li key={c.id}>{c.body}</li>)}</ul>
    </section>
  );
}
// loading.jsx — fallback automático enquanto QUALQUER parte do segmento / carrega
export default function Loading() {
  return <p role="status">⏳ Carregando a página…</p>;
}

Por que isso deixa a página mais rápida

Sem streaming, o tempo até o primeiro byte de conteúdo útil (TTFB + render completo) inclui todos os awaits da página. Com Suspense, o navegador já recebe e pinta o shell no primeiro pacote — o LCP (maior conteúdo visível) acontece cedo, mesmo que os dados lentos ainda estejam vindo. O Next.js também manda os blocos suspensos com hidden e um script inline que faz a troca no lugar, então não há "pulo" de layout nem recarregamento.

Quando dá errado

Erro real de build: a página usava useSearchParams() (hook de cliente) numa rota estática, sem Suspense. O Next.js para o build inteiro com esta mensagem — porque sem Suspense não há como fazer streaming dessa parte:
Error: useSearchParams() should be wrapped in a suspense boundary at page "/dashboard".
Read more: https://nextjs.org/docs/messages/missing-suspense-with-csr-bailout
→ Solução: envolva o componente que usa useSearchParams em <Suspense>
   (ou force a rota dinâmica com export const dynamic = 'force-dynamic').
Outro clássico: o fallback nunca aparece e a página trava em branco. Quase sempre o componente "lento" na verdade lançou um erro (fetch fora do ar, JSON inválido) e não suspendeu — o erro sobe para o error.jsx mais próximo. Verifique o network e o try/catch dentro do componente async:
Error: Failed to fetch `https://api-quebrada…` → Unhandled Runtime Error
→ trate no componente: try { … } catch { return <p>Não consegui carregar.</p> }
