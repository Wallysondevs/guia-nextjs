Performance e Core Web Vitals: LCP, INP e CLS

"Rápido" é subjetivo — o Google mede a experiência real do usuário com três números: LCP (quando o maior conteúdo apareceu), INP (quanto tempo a página levou para reagir ao clique) e CLS (quanto a página pulou de lugar). Nesta aula a Ana aprende a medir esses números no próprio Next.js e a consertar os três pecados mais comuns.

Você vai aprender
  • Os 3 Core Web Vitals e os valores "bons" de cada um (LCP < 2.5s, INP < 200ms, CLS < 0.1)
  • O indicador de velocidade que o Next.js mostra no canto em dev (e o Speed Insights em produção)
  • Lighthouse no DevTools e no pagespeed.web.dev
  • Correções típicas: priority no LCP, next/script para terceiros, useTransition para buscas, reserva de espaço contra CLS
  • next build já avisa quando uma página ficou pesada

A ideia: a loja física e os três combinado

Pense numa loja física. O LCP é o tempo até a vitrine principal estar montada — se a vitrine demora, o cliente vai embora antes de ver nada. No site, a vitrine é a maior imagem/texto acima da dobra; deixe-a com priority no <Image> e a fonte com next/font (sem bloqueio), que o LCP cai.

O INP é o tempo entre o cliente apontar para um produto e o atendente reagir. No site, é o clique no botão e a resposta da página. Se o clique dispara um trabalho pesado no mesmo frame (filtrar uma lista gigante, navegar), a página "congela" e o INP piora. A saída é o useTransition (marca a atualização como não urgente) e o streaming/Suspense da aula anterior.

E o CLS é a prateleira que muda de lugar enquanto o cliente olha — medida de "estabilidade visual". A causa nº 1 é imagem/fonte sem tamanho reservado: conserte com width/height no <Image> e next/font (aula anterior). Anúncios que empurram conteúdo também entram aqui.

Ana e a fila do caixa: a loja é rápida quando ninguém espera

A loja da Ana pode ter a vitrine linda, mas se o caixa demora três minutos, o cliente reclama. Na web acontece o mesmo: o LCP mede quanto tempo leva para o conteúdo principal aparecer (a vitrine chegando), o INP mede se os cliques respondem na hora (o caixa ágil) e o CLS mede se a página "pula" enquanto carrega (a prateleira que muda de lugar). Esses três são os Core Web Vitals — as três filas do caixa do site.

A Ana mede no próprio projeto com o next build e com o relatório da Vercel, e corrige o que pesa: imagem grande demais → next/image; JavaScript demais → componentes menores e lazy; fonte que chega tarde → next/font. Performance não é detalhe: é a diferença entre a loja dela e a loja em que o cliente desiste de entrar.

Correções rápidas que resolvem 80% dos casos

'use client';
import { useState, useTransition } from 'react';

export default function BuscaClient({ produtos }) {
  const [filtro, setFiltro] = useState('');
  const [resultado, setResultado] = useState(produtos);
  const [pendente, startTransition] = useTransition(); // clique não trava a página

  function aoDigitar(e) {
    const valor = e.target.value;
    setFiltro(valor); // urgente: atualiza o input na hora
    startTransition(() => {
      setResultado(produtos.filter(p => p.nome.includes(valor))); // pesado: pode esperar
    });
  }

  return (
    <>
      <input value={filtro} onChange={aoDigitar} placeholder="Buscar…" />
      {pendente && <small>procurando…</small>}
      <ul>{resultado.map(p => <li key={p.id}>{p.nome}</li>)}</ul>
    </>
  );
}

Quando dá errado

Erro real de CLS: a Ana colocou um banner de cookies depois que a página já pintou, e o conteúdo pulou para baixo. O Lighthouse acusa:
CLS: 0.25 (ruim) — "Evite grandes mudanças de layout"
  Elemento que mais shiftou: <img src="/banner.jpg"> sem width/height
→ reserve espaço (width/height/fill) ou carregue o banner com priority/antes da pintura.
LCP alto no relatório: a maior imagem da página era um carrossel carregado por biblioteca de cliente pesada. O build avisa:
ƒ /carrossel   First Load JS 380 kB  ⚠ acima do orçamento sugerido (170 kB)
→ troque por dynamic(..., { ssr: false }) ou imagens estáticas com <Image priority>.
